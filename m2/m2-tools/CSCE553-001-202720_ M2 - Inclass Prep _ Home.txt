      This is a preparation for the M2 assignment. You will learn to use the various tools.

      3.1 Variables    worth knowing
              FACULTY SUPPORT STUDENT SUPPORT                                  MY BOOKS            MY GRADES    MY COURSES 




       %{variable}                 What it measures
       http_code                   Status (200, 401, 502, …). Empty body with 401 is still a completed HTTP call
       time_namelookup             DNS. High on first call, often ~0 later
       time_connect                TCP connect (includes DNS). Jump here often means network or the host is down
       time_appconnect             TLS handshake (HTTPS only). 0 on plain http://127.0.0.1
       time_pretransfer            Up to just before curl sends the request body / finishes request setup
       time_starttransfer          Time to first byte (TTFB): network + server work before the body starts
       time_total                  Whole transfer, including reading the body. Closest to “how long the client waited”
       size_download               Response body bytes. This is your payload note for M2
       size_header                 Response header bytes
       num_connects                New connections used. 1 is normal for a single curl
       url_effective               Final URL after redirects
       errormsg                    Transfer error text (timeouts, DNS fail). Empty on HTTP 4xx/5xx — those still have an http_code
       redirect_url                If you were bounced (login page HTML instead of JSON — wrong path)

      Rule of thumb: server-side work sits mostly in time_starttransfer − time_pretransfer (the wait after the request is sent,
      before the first byte). Download of a large body sits in time_total − time_starttransfer. Cold start inflates all of these,
      especially TTFB.

      6. Resource signals — API CPU and memory



      M2 needs a chain of evidence: load → service numbers → resource numbers, on the same clock. “The API got slow” is not
      a claim until a resource moved with it.

      Use one machine’s clock (your laptop). Screenshot so a clock or the filename carries the time: render-cpu-H-prep-

      6.0 What to record (gauges, not a movie)




      Task Manager, Activity Monitor, Resource Monitor, top, and docker stats are live gauges (about a one-second average).
      They are not lab recorders. You do not transcribe the needle every second. You write a timestamped sample.

      One line is enough:
      15:47:35      L-read-c8      mid-stage      process=python/uvicorn     CPU=72%     RSS=180 MB




      For the stage you will argue from in M2 (today: idle vs one curl), take three samples when you can:

         1. Idle — a few seconds with no load.
         2. Mid-work — while the request (later: the 60 s window) is running.
         3. After recover — 30–60 s later: did CPU/memory come back down?

      If the value jumps, record a range (CPU 60–80%) and still keep the clock. Instantaneous is fine. “It looked high” is not.

      7.2 How many connections are open?




      SELECT count(*) AS connections
      FROM pg_stat_activity;




      SELECT state, count(*)
      FROM pg_stat_activity
      GROUP BY state
      ORDER BY count(*) DESC;




      idle vs active matters: a connection pool can hold many idle backends. A count of 1–8 at rest is common. A count that
      climbs toward the host max connections during load is a bottleneck candidate later.

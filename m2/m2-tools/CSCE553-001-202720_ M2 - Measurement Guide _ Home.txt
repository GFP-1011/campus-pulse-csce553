      Performance


      CSCE 553 · Fall 2026

      Use this with M2 — Baseline Performance.

      You will: pick parameters → pick tools → design a stair-step → run it → save CSVs and resource notes → write the report.

      The supported driver is a Python 3.12+ stdlib script (below). hey, Locust, and k6 are allowed if they emit the same numbers.
      You still need resource signals; a load-tool screenshot is not enough.


      0. What “done” looks like



      A teammate can:

         1. Read m2/m2-report.md and see a prediction dated before the sweep.
         2. Re-run python load_baseline.py ... against your hosted URL and localhost.
         3. Open m2/results/*.csv and rebuild the three required charts.
         4. Point to CPU / memory / connections (or disk) at the same clock time as a load stage.

      Architecture stays: load generator → API → Postgres. No new products.

      1.1 Load (independent variable)

       concurrency N               flight                   request when the last returns)
       Duration                    Steady-state window      10 s warmup + 60 s measure

      Closed-loop concurrency is what this script does. It is not the same as “N users on the website.” Convert in the worksheet:
      RPS ≈ active users × actions / seconds.

      Little’s Law (check your own table): L ≈ throughput × mean latency. If you measured 40 successful req/s at 0.25 s mean
      latency, expect ~10 requests in flight. If concurrency was 16 and L is 10, clients were idle or the server was rejecting work —
      say so.

      1.2 Service behavior (dependent variables)




       Name                Definition                                                               Do not substitute
       Throughput          Count of HTTP 2xx/3xx in the measure window ÷ wall seconds               Do not count 5xx as successful RPS

       Error rate
                           attempts                                                                 that is still an error for the test

      Cold-start latency is a separate one-off measurement, not part of the percentile of a 60 s warm run. Mix them and p99
      becomes “Render woke up.”

       Disk I/O                Often invisible on free PaaS; say “not observable”
                                                                                             Docker stats block I/O
       Host sleep              First request after 15 min idle                               Does not apply

      You need at least two resource signals for the hosted stair-step. “The API got slow” without a resource is incomplete.

      1.4 Objectives (derived, not raw)




      An SLI is a user-facing signal (latency of the list endpoint; success ratio). An SLO is a threshold on that SLI. You propose one
      SLO from data in the report. You do not need Prometheus.

      2.4 What not to use as the only instrument                                                                       




      Browser DevTools Network tab (too few requests). Postman runner (hard to get percentiles). Hitting the HTML pages instead
      of /api/... (you will measure templates and static files, not the API you will scale later).


      3. Designing the experiments




      3.1 Write the model first




      Fill the 10K / 1M / 100M worksheet in a file m2/results/prediction.md before the first 60 s run. Commit it, or paste a
      screenshot of the file with a timestamp. Then predict:

          First limit: ________ (e.g. Render CPU, DB connections, API memory, request queue in the framework).

      A reasonable M1 guess: one 0.1 CPU / 512 MB web process saturates before 500 MB Postgres, on the read path, unless
      you open a new DB connection per request (then connections may win). You must justify your guess from how your app
      uses the DB (pool vs connect-per-request). If you do not know, open the code and look; “AI wrote it” is not an assumption.

      3.2 Factors you hold constant




      For a given curve (throughput vs N):

            Same git commit
            Same endpoint and JSON body
            Same auth token (refresh if 401s appear — then note it)
            Same mix (100% read for the main sweep)
            Same region / laptop on AC power

      Vary only concurrency (and environment H vs L as a separate curve).

      3.3 Factor you do not hide                                                                                       




      Render free web services sleep after ~15 minutes idle and take ~1 minute to wake. That is a shape effect (burst of latency),
      not your steady-state capacity. Design:

         1. Measure cold start once (required).
         2. curl /health until it is fast.
         3. Only then start warmup + 60 s stages.

      Series L answers: “If the host did not sleep and had my laptop’s CPU, where is the knee?” Do not declare H “broken” because
      of sleep; declare sleep a confound for p99 unless you warmed up.

       Social             GET /api/messages

       commerce           q=                                                                                          /health

      3.6 Repeatability




      Repeat the last healthy stage. If RPS differs by more than ~20%, look for: sleep mid-test, token expiry, laptop thermal
      throttle, someone else using the DB. Report both runs; do not silently pick the prettier one.


      4. Executing the experiments



      Do this in order. Do not start Locust “to see what happens” before the prediction file exists.

      4.1 Prep (both environments)




         1. Confirm M1 still works: hosted curl health + login + one read (same as M1 evidence).
         2. Seed the read-path table if the list/search response is empty or tiny ([], a handful of rows). An empty database is not
            the workload you are modeling. Copy seed_data.py from the handout pack and POST enough rows that curl -w "%
            {size_download}" on the read path is stable and non-trivial (on the order of 50 posts or products). Use the same write
            API the app already has; this is sequential inserts, not a load test. Re-running the script adds more rows — run it once,
            then leave the table alone for the read sweep.
         3. Create m2/results/ in the repo. Add m2/results/*.png to git if you want screenshots; keep .env gitignored.
         4. Write m2/results/prediction.md.
         5. Open Render metrics and Supabase reports in a browser; leave them open.

      not rewriting the app.

      4.4 If a stage explodes




      Stop. Record the error rate and p99. That row is the measured limit. You do not need a perfect curve on the far side of
      saturation. Recover (wait), repeat the previous stage once, then move to writes/mix if you still can, or stop hosted load if the
      project is unhealthy.

      6. Presenting



      m2/m2-report.md is a measurement paper, not a diary. Suggested headings (match the assignment rubric):

         1. System under test — one diagram, commit, hosted URL, local command.
         2. Workload model — assumptions; 10K / 1M / 100M table; predicted first limit.
         3. Method — driver and version (python --version), endpoints, stages, stop rules, H vs L.
         4. Results — tables + three figures. Cold-start row. Mix/write if they differ from read.
         5. Resources — aligned notes; which signal moved with p99.
         6. Claim — one bottleneck. Use mix if writes saturated something else.
         7. SLO — eligible events, T, E, pass/fail on H at the last healthy stage.
         8. Revise — gap vs prediction; what the 1M and 100M columns would require (more CPU, pooling, cache, …) without
            implementing them.
         9. Confounds — sleep, shared tenancy, laptop, clock, token expiry.
        10. Repro — exact commands.

      Tone: numbers, then interpretation. “p99 rose from 80 ms at N=4 to 2.1 s at N=16 while Render CPU sat at ~90% and DB
      connections stayed at 8” is a claim. “The cloud is slow” is not.

      Little’s Law paragraph: pick one healthy stage, show L ≈ RPS × mean latency, compare to concurrency.

      Do not recommend buying Render Pro as the finding. Cost is a system property: the free host is a limit. The next milestone
      is whether a cache (or index, or pool) moves the bottleneck — after this baseline exists.

      7. Supported driver (copy into the repo)                                                                              




      Save the provided load_baseline.py at the repo root. Read and review it before you run it. You may need to customize it for
      your app.

      Save the provided login.py at the repo root. It can be used to get the JWT token. You may need to customize it if your JSON
      uses another key, print body once and adapt.

      9. What not to do                                                                                                        




            Do not pay for hosting to flatten the hosted curve.
            Do not add Redis “just to have a cache number.” That is the next architecture change.
            Do not load-test the HTML UI as a substitute for the JSON API.
            Do not discard the run that hit the stop rule — it is the measured limit.

      When prediction, CSVs, two environments, resource timestamps, and a bottleneck sentence exist, go back to the assignment
      submission list.

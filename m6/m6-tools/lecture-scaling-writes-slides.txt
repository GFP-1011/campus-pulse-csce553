The point is the shape: a hundred times more writes, concentrated in time, all aimed at the same database.

WHY ONE DATABASE RUNS OUT
Each write costs the database real work on one machine

One machine has a fixed budget: CPU, disk writes per second, and time spent waiting on locks. When writes arrive faster than that budget, they queue. Shoppers see slow or failed clicks.
A bigger machine raises the limit, but there is always a largest machine, and its price grows faster than its speed.
7
Open the box on a single INSERT. The database locks the row so two people cannot change it at once. It changes the table. It updates every index on that table: the indexes we added in the first lecture make reads faster but make each write do more. Finally it records the change in its log and waits for the disk to confirm, so the change survives a crash. All of this happens on one machine with a fixed amount of CPU, disk speed and memory. A bigger machine raises the ceiling but does not remove it, and the price climbs faster than the capacity.

A common first reaction: add copies of the database (read replicas). Reads can go to any copy, so read capacity grows with each copy. But a write must happen on the main database and then be replayed on every copy, otherwise the copies would be wrong. So the main database still does all the writes. Indexes and caches also help reads only. The conclusion on the bottom bar is the key sentence of the lecture so far.

Same five tables on each database, but each database holds only some customers' rows. A write for a customer goes only to the database that owns that customer. With two databases, each one handles about half the writes; with four, about a quarter. Analogy: a grocery store with one checkout lane versus several lanes. Each shopper uses one lane, and the lanes work at the same time.

PRINCIPLE: KEEP TOGETHER WHAT IS WRITTEN TOGETHER
Store a customer's cart and orders on that customer's shard
users  Maria
cart_items  Maria's 2 items
orders  Maria's order
order_items  that order's items
Shard A
Do: route child rows by their owner (user_id), not by their own id.
Why: checkout stays one ordinary transaction on one database.
Don't: put an order on one shard and its items on another.
If you must, use detail-first publishing from the master-detail lecture.
Consequence for the schema: order_items gets its own user_id column, so it can be routed like everything else.
13
Checkout writes an order, its items, and deletes the cart, all at once, and all of it must succeed or fail together. If all of Maria's rows live on shard A, checkout is one ordinary transaction on one database, exactly like the master-detail insert from the earlier lecture. If the order lived on A and the items on B, no single database could make them succeed or fail together; we would need the detail-first publishing trick from that lecture, and cleanup for orphans. So: route child rows by the owner, not by their own id. This means order_items needs a user_id column too.

Do: copy tables that are small, read by everyone, and rarely written.
Cost: each change is written to every shard.
Win: cart and order queries still join with products on one database.
Don't: copy data that changes on every purchase, such as stock counts.
Ownership decides placement: owned rows go to the owner's shard; shared, read-mostly rows go everywhere.
14
Products are shared by every customer, so they cannot 'belong' to one shard. But they are small and change rarely (an admin edits a price now and then), while customers read them constantly. So keep a full copy on every shard. The cost: a product change must be applied to every shard. The win: carts and orders can still join with products locally, and prices are copied into order_items at checkout, so later price changes don't alter old orders. This only works for read-mostly data. A table that changes on every purchase, such as a stock counter, does not fit this rule.

Capacity = the busiest shard
If shard A gets 70% of the writes, it hits its limit while shard B sits partly idle. Adding shards doesn't fix a rule that piles customers into one of them.
Don't pick a key whose values cluster. Real-world names, cities, and categories always cluster.
15
The 10 most common US surnames in the 2010 Census: Smith, Johnson, Williams, Brown, Jones, Garcia, Miller, Davis, Rodriguez, Martinez. Seven of them start with A through M. The alphabet splits evenly; people do not. And your customers are not the national average: a store popular in a community where many people share a surname (Nguyen, Kim, Patel) can overload a single shard. The key lesson: the system is only as fast as its busiest shard. An idle shard B does not help a shard A that is overloaded.

Maria Lopez gets married and becomes Maria Smith. The rule now says shard B, but her user row, carts, and past orders are on shard A. Either every one of her rows moves across databases, or the rule stops being true. The same happens when you try to fix the imbalance by moving the boundary from M to K: every customer between L and M moves. Both say the same thing: the key should be something that never changes.

A second common proposal: customers 1 to 100,000 on shard A, 100,001 and up on shard B. The split by count looks even. But who is buying today? Mostly recent and new customers: new sign-ups, first carts, welcome-discount orders. They all land on the newest shard. The old shard holds many rows but few writes. Even rows, uneven work. And every time the newest shard fills, the hot spot simply moves to the next one.

A hash function turns any value into a large, random-looking number. Two properties matter: the same input always gives the same number, so the rule is repeatable; and nearby inputs give unrelated numbers, so customers 1001 and 1002 do not end up together. Take the remainder after dividing by the number of shards: with two shards, remainder 0 means shard A, 1 means shard B. The hash values on this slide are real (first 8 hex digits of MD5, as a number). With a handful of customers the split looks lumpy; with thousands it evens out. In our test with 2,000 sign-ups, the split was 1,008 and 992.

PRINCIPLE: PLAN FOR GROWTH
Hash into many fixed buckets, then map buckets to shards
Today: 64 buckets, 2 shards
Later: add shard C
A  B  C   one square = one bucket
bucket = hash(id) ÷ 64, remainder. Never changes.
A small map says which shard owns each bucket. Only the map changes.
Adding a shard moves whole buckets, not two thirds of all rows.
Don't divide by the number of shards directly. Divide by a fixed bucket count and keep a bucket-to-shard map.
20
Problem with 'remainder by number of shards': when you go from 2 shards to 3, the remainder changes for most customers. For a random hash, it stays the same for only about 1 in 3 customers, so about two thirds of all rows would move. Fix: divide by a fixed number of buckets that never changes, say 64. Each customer always has the same bucket. A small table says which shard owns each bucket. To add a shard, hand it some buckets; only the rows in those buckets move, and they move as whole groups. In the picture, going to three shards moves about a third of the buckets, which is the least possible.

bd72cdf2-1eb2-443a-bee1-dd81601f32b6
4961e826-a967-473a-96d4-86f92452719b
Do: use UUIDs for every table's id. Don't depend on one shared counter, or the bottleneck returns.
21
Today our tables use auto-increment integer ids: the database hands out 1, 2, 3. With two shards, each shard has its own counter, so shard A and shard B both create order 17; any report that combines them is confused. One shared counter would fix that, but then every write in the system stops to ask one place for the next number: the single bottleneck we were trying to remove. The fix is a UUID: a 128-bit random id that any machine can make on its own; the chance of two being equal is negligible. Bonus: the id exists before the INSERT, so we can route by it. UUIDs are bigger and unordered, which costs some index space; we accept that.

A gap in the plan: at login the customer types an email, not an id. Which shard should we ask? We keep one small table, the directory, that maps email to customer id; the id gives the bucket and the bucket map gives the shard. The directory also guarantees each email is used once across the whole system, which a uniqueness rule inside one shard cannot do. Isn't this one central table a new bottleneck? It is touched at sign-up and login only, which are rare compared to cart writes. After login, keep the id and shard in the session.

PRINCIPLE: FAIL LOUDLY
Make each shard refuse rows that do not belong to it
Shard A
accepts buckets 0–31 only
Customer in bucket 16
✓ accepted
Customer in bucket 37
✗ rejected: routing bug caught
Do: put a check on the customer table of each shard.
Carts, orders and items are covered automatically: they must point to a customer on the same shard.
A wrong-shard write should be an error today, not a missing order next month.
23
With routing in the app, one bug can write a customer to the wrong shard. Nothing breaks at first; later the customer's orders seem to vanish, because every read goes to the correct shard and finds nothing. Give each shard a rule: a customer row is accepted only if its bucket is one this shard owns. Then the cart, order, and item rows are covered too, because they must point at a customer row on the same database. A routing bug becomes an immediate error instead of silent lost data.

Be honest about the price. Anything keyed by one customer is now easy and fast. Anything that spans customers is now spread over every shard: 'all pending orders', 'today's revenue', 'best-selling product'. You must ask every shard and combine the answers. Also, hashing spreads customers, not the work of one customer: a reseller bot hammering one account still lands on one shard. These are topics for later lectures; for now, notice which of your app's pages are per-customer and which are global.

PRINCIPLE: SHARD LAST
Measure first, and try the cheaper fixes before you shard
1
Measure: are writes really the bottleneck?
2
Fix slow writes; drop unused indexes
3
Combine many small writes into fewer
4
Move to a bigger database plan
5
Shard
Don't shard on a hunch. Each step to the left is cheaper and easier to undo than the next.
25
Sharding is hard to undo and touches every query in the app, so it is the last step, not the first. First confirm writes are the bottleneck by measuring. Then try the cheap fixes: speed up slow write statements and drop indexes nobody uses (each index costs every write), group many small writes into fewer statements, and move to a bigger database plan. Shard when those are exhausted, or when you can see growth that will exhaust them.

STEP 1
Confirm that writes are your bottleneck before you change anything
-- Turn on statement statistics (once per project)
create extension if not exists pg_stat_statements
  with schema extensions;
 
-- Which write statements cost the most time?
select left(query, 60)         as statement,
       calls,
       round(total_exec_time)  as total_ms
from extensions.pg_stat_statements
where query ~* '^\s*(insert|update|delete)'
order by total_exec_time desc
limit 10;

SQL Editor: run the query on the left.

-- shard_schema.sql  (excerpt; same file on every shard)
create or replace function shard_bucket(u uuid)
returns int language sql immutable as $$
  select (('x' || substr(md5(u::text), 1, 8))
          ::bit(32)::bigint % 64)::int
$$;
 
create table order_items (
  id         uuid primary key default gen_random_uuid(),
  user_id    uuid not null,            -- new: the owner
  order_id   uuid not null,
  product_id uuid not null references products(id),
  quantity   int  not null,
  price      numeric(10,2) not null,
  foreign key (user_id, order_id)
    references orders(user_id, id)
);
One file, every shard. Paste it into each project's SQL Editor.

Every owned table has user_id.

32
Keep one file, shard_schema.sql, in your repo, and paste it into the SQL Editor of each shard. Never edit one shard by hand; drift between shards causes bugs that only appear for some customers. Shown here are the two parts that are new compared with your current schema. First, shard_bucket: md5 of the id, first 8 hex digits as a number, remainder after dividing by 64. It is marked IMMUTABLE because the same input always gives the same output. Second, order_items now carries user_id, and its foreign key points to orders by (user_id, id), so an item can only attach to an order of the same customer on the same shard. ids are uuid. The full file is in the handout.

STEP 9 · WRITES
Check out with one stored procedure on the customer's shard
create or replace function checkout(p_user uuid)
returns uuid language plpgsql as $$
declare v_order uuid := gen_random_uuid();
begin
  perform 1 from cart_items
    where user_id = p_user for update;
  if not found then raise exception 'cart is empty'; end if;
  insert into orders (id, user_id) values (v_order, p_user);
  insert into order_items
    (user_id, order_id, product_id, quantity, price)
  select p_user, v_order, c.product_id, c.quantity, p.price
  from cart_items c join products p on p.id = c.product_id
  where c.user_id = p_user;
  update orders set total_amount =
    (select sum(quantity * price) from order_items
     where order_id = v_order)
  where id = v_order;
  delete from cart_items where user_id = p_user;
  return v_order;
end $$;
The app's only call:
select checkout(
 'bd72cdf2-1eb2-443a-bee1-dd81601f32b6');
One database, one transaction
Locks the cart so it can't change mid-checkout
Price copied from the local products copy
All or nothing: any error undoes every step
39
Checkout is the master-detail insert from earlier, and because everything belongs to one customer on one shard, it is a single local transaction. Put it in a stored procedure (the second lecture) installed on every shard by shard_schema.sql. It locks the cart rows so the cart can't change mid-checkout, creates the order, copies each cart line into order_items with the product's current price, computes the total, and empties the cart. A Postgres function runs as one transaction: if any step fails, none of it happens. The app makes one call on the customer's shard.

create or replace function register(
